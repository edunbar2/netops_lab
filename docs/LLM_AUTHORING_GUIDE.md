# LLM Authoring Guide for Topologies and Scenarios

This guide explains how an LLM should create new topologies, scenarios, and labs for the GNS3 lab generator.

The goal is to create data-driven labs that work without Python code changes.

## Core design

The generator consumes:

```text
catalogs/ccnp_encor_lab_catalog.json
config_templates/*.j2
```

The catalog has three main sections:

```json
{
  "templates": {},
  "topologies": {},
  "scenarios": {}
}
```

A lab is generated by:

```text
1. Choose scenario.
2. Load the scenario's topology.
3. Apply scenario data_patches to topology/node variables.
4. Render each node's config_template with Jinja.
5. Create GNS3 project/nodes/links.
6. Start nodes and push configs where supported.
7. Write student brief, clean configs, starter/faulty configs, answer key, and manifest.
```

## Topology object schema

A topology must look like this:

```json
"topology_id": {
  "description": "Human-readable description.",
  "exam_blueprints": ["ENCOR"],
  "difficulty_band": "intermediate",
  "vars": {},
  "nodes": {},
  "links": []
}
```

Recommended optional metadata:

```text
exam_blueprints
technology_domains
difficulty_band
default_template_family
notes
```

## Node schema

Every node should look like this:

```json
"R1": {
  "template": "iol3",
  "role": "router",
  "device_os": "ios",
  "push_config": true,
  "x": 0,
  "y": 0,
  "config_template": "ios_router.j2",
  "vars": {}
}
```

### Required node fields

```text
template
role
device_os
push_config
x
y
vars
```

### Config template fields

Use one of:

```text
config_template
config_template_by_host_type
```

Use `config_template` for routers, switches, firewalls, and appliances.

Use `config_template_by_host_type` for generic host nodes:

```json
"config_template_by_host_type": {
  "alpine": "alpine_host_setup.j2",
  "rhel9": "rhel_host_setup.j2",
  "vpcs": "vpcs_host.j2"
}
```

## Interface naming

Use the interface names expected by the image family.

Recommended naming:

```text
IOL/IOL-L2:      Ethernet0/0, Ethernet0/1, Ethernet0/2
IOSv:            Gi0/0, Gi0/1
IOSvL2:          Gi0/0, Gi0/1
CSR1000v/8000v:  Ethernet0, Ethernet1 or vendor-specific names matching your GNS3 template
ASAv:            GigabitEthernet0/1, GigabitEthernet0/2
NX-OSv:          Ethernet1/1, Ethernet1/2
```

Do not mix IOSv `Gi0/x` names into an IOL topology.

## Link schema

A link must look like this:

```json
{
  "a": "R1",
  "a_adapter": 0,
  "b": "R2",
  "b_adapter": 0,
  "label": "R1 Ethernet0/0 <-> R2 Ethernet0/0"
}
```

Rules:

```text
a and b must match node names.
a_adapter and b_adapter must be integers.
Adapter numbers must match the intended interface order in GNS3.
label should be human-readable and match the config interface names.
```

## Scenario schema

A scenario must look like this:

```json
"scenario_id": {
  "title": "OSPF Area Mismatch",
  "topology": "ospf_multi_area_enterprise",
  "exam_blueprints": ["ENCOR", "ENARSI"],
  "domain": "Infrastructure",
  "topic": "OSPF",
  "difficulty": "easy",
  "symptom": "R1 and R2 do not form a full OSPF adjacency.",
  "faults": [
    {
      "device": "R1",
      "fault": "Ethernet0/0 is in OSPF area 1 instead of area 0.",
      "fix": "Set Ethernet0/0 back to area 0."
    }
  ],
  "data_patches": [],
  "verification": [
    "show ip ospf neighbor",
    "show ip ospf interface brief"
  ]
}
```

## Required scenario fields

```text
title
topology
domain
topic
difficulty
symptom
faults
verification
```

## Recommended scenario metadata

```text
exam_blueprints
exam_objectives
technology_tags
estimated_minutes
requires_templates
lab_type
```

Example:

```json
"exam_blueprints": ["CCNA", "ENCOR"],
"exam_objectives": ["ENCOR 3.1", "CCNA 2.1"],
"technology_tags": ["ospf", "routing", "adjacency"],
"estimated_minutes": 15,
"requires_templates": ["iol3", "iol2", "alpine"],
"lab_type": "troubleshooting"
```

## Data patches

Prefer `data_patches` over text patches. Data patches modify the topology model before config rendering.

Supported actions:

```text
set
delete
append
extend
```

### set

```json
{
  "device": "R1",
  "action": "set",
  "path": "vars.ospf_processes.0.networks.0",
  "value": "10.0.0.0 0.0.0.3 area 1"
}
```

### delete

```json
{
  "device": "R1",
  "action": "delete",
  "path": "vars.bgp_processes.0.redistribute.0"
}
```

### append

```json
{
  "device": "R1",
  "action": "append",
  "path": "vars.extra_config",
  "value": "ip access-list extended TEST\n deny ip any any"
}
```

### extend

```json
{
  "device": "R1",
  "action": "extend",
  "path": "vars.interfaces.0.lines",
  "values": [
    "ip ospf cost 500",
    "ip ospf network point-to-point"
  ]
}
```

## Text patches

Use text patches only when the Jinja data model cannot express the fault.

Supported actions:

```text
replace
remove
append
append_before_end
regex_replace
```

Text patches are more fragile because they depend on exact rendered config text.

## Clean/faulty config model

The generator creates:

```text
clean_configs/  known-good configs
configs/        faulty scenario configs
```

A scenario must be designed so:

```text
clean config works
faulty config creates the stated symptom
answer key identifies the precise root cause
verification commands help isolate the issue
```

## Push behavior

Currently:

```text
IOS/IOL nodes: auto-push supported
Linux hosts: config notes generated, not automatically pushed
ASAv: config generated, not automatically pushed by default
NX-OSv: config generated, not automatically pushed by default
```

For new topologies, set:

```json
"push_config": true
```

only when the current pusher can safely configure the device OS.

## Exam filtering

Every new scenario should include `exam_blueprints`.

Recommended values:

```text
CCNA
ENCOR
ENARSI
SCOR
DEVASC
CUSTOM
```

A scenario can belong to multiple exams:

```json
"exam_blueprints": ["CCNA", "ENCOR"]
```

A topology can also include `exam_blueprints`, but filtering should primarily happen at the scenario level.

## Difficulty levels

Use:

```text
intro
easy
medium
hard
expert
```

Existing scenarios may use `easy`, `medium`, and `hard`. Prefer those unless adding beginner CCNA-specific labs.

## Scenario ID conventions

Use lowercase snake_case.

Recommended prefixes:

```text
l2_       Layer 2 switching
l3_       Layer 3 routing
bgp_      BGP
ospf_     OSPF if not using l3_
svc_      IP services
sec_      Security
na_       Network assurance
auto_     Automation
virt_     Virtualization
dc_       Data center / NX-OS
fw_       Firewall
ccna_     CCNA-specific intro labs
```

Examples:

```text
ccna_vlan_access_port_wrong
ccna_static_route_missing
encor_bgp_local_pref_wrong
enarsi_ospf_lsa_filtering_issue
```

## LLM prompt for authoring new scenarios

Use this prompt:

```text
You are authoring data-driven labs for the GNS3 lab generator.

Create valid JSON entries for `ccnp_encor_lab_catalog.json`.

Rules:
- Do not modify Python code.
- Use existing templates and Jinja templates unless explicitly asked to create new `.j2` files.
- Prefer data_patches over config_patches.
- Include exam_blueprints on every scenario.
- Include clear symptom, faults, fixes, and verification commands.
- Ensure interface names match the topology's image family.
- Keep scenario IDs lowercase snake_case.
- Return valid JSON only.
```

## LLM prompt for authoring a new topology

```text
You are authoring a new topology for the GNS3 lab generator.

Create a valid JSON topology object.

Rules:
- Use existing catalog template keys.
- Include description, exam_blueprints, vars, nodes, and links.
- Each node must include template, role, device_os, push_config, x, y, config_template or config_template_by_host_type, and vars.
- Use correct interface names for each image family.
- Links must reference valid nodes and adapter numbers.
- Prefer IOL3 for routers and IOL2 for switches unless the lab requires IOSv, IOS XE, ASAv, or NX-OSv.
- Return valid JSON only.
```

## Review checklist for generated content

Before accepting generated topology/scenario JSON, verify:

```text
All node template keys exist in catalog templates.
All scenario topology IDs exist.
All data patch paths are valid.
All interface names match the image family.
All links reference real nodes.
All adapter numbers are plausible.
At least one verification command directly exposes the fault.
The answer key fault/fix matches the injected data_patch.
Exam blueprint tags are present.
```
